# ko-design-md — Repository Analysis for a Samsung One UI Contribution

> Read-only analysis. No production files were modified to produce this document.
> Scope: how this catalog represents a design system, what a new entry must ship,
> and which existing entries best model a Samsung One UI (OS-level) contribution.

---

## 1. How a new design system / service is represented

A single catalog entry is **one markdown file plus a set of derived artifacts**, keyed by a `slug`:

| Artifact | Path | Role | Hand-authored? |
|---|---|---|---|
| Design doc | `services/{slug}.md` | Source of truth — YAML frontmatter + Stitch v0.1 body | **Yes** (the only true source) |
| Token sidecar | `services/{slug}.tokens.json` | Machine-readable color/type/spacing/radius cards for the detail page | No — generated by `pnpm tokens:build {slug}` from the md |
| Light preview | `public/preview/{slug}/light.html` | Self-contained component demo (`data-theme="light"`) | Yes (via preview author) |
| Dark preview | `public/preview/{slug}/dark.html` | Same, `data-theme="dark"` — route default | Yes |
| OG image | `public/og/{slug}.png` | Social card | No — generated by `pnpm build:og` |
| Logo (optional) | `public/logos/{slug}.{svg,png,webp,avif}` | Catalog grid + OG mark | User-supplied |

The md is authoritative; everything else is derivable from it. The site (TanStack Start) serves each entry at `/services/{slug}` (HTML detail page with **Live Preview** + **DESIGN.md** tabs) and at `/services/{slug}/llms.txt` (raw `text/plain` for LLMs/agents).

The body follows the **Stitch v0.1** section structure (English `##` headings, in a fixed relative order), but frontmatter is catalog-specific (Stitch's own token-YAML-in-frontmatter is NOT used — tokens live in body sections).

## 2. Required files & directories for a new contribution

Minimum to pass CI for a new entry `{slug}`:

1. `services/{slug}.md` — required.
2. `services/{slug}.tokens.json` — required (drift-gated by `pnpm tokens:check`; must be regenerated, not hand-edited).
3. `public/preview/{slug}/light.html` **and** `public/preview/{slug}/dark.html` — both required.
4. `public/og/{slug}.png` — generated; the index still renders without it (route falls back), but the pipeline builds it.
5. `public/logos/{slug}.{ext}` — optional; if `logo` frontmatter is set it must resolve.
6. For `lang: both`: add `services/{slug}.en.md` (and it gets its own tokens sidecar / preview reuse).

The shared preview runtime (`public/preview/_runtime/tokens.css`, `iframe.js`) already exists — new entries reference it by absolute path, never copy it.

## 3. Frontmatter / schema conventions

Schema is defined in `src/lib/content-types.ts` (`ServiceFrontmatter`) and validated strictly in `src/lib/content-parser.ts`. Required keys:

```yaml
name: 삼성 One UI            # Korean brand display name
design_system_name: One UI  # optional — distinct design-system product name
slug: samsung-one-ui        # ^[a-z0-9-]+$ , equals filename stem
category: developer         # ∈ CATEGORIES const (see below)
last_updated: "2026-08-13"  # ^\d{4}-\d{2}-\d{2}$ (quote it — gray-matter parses bare dates as Date objects → throws)
created_at: "2026-08-13"    # same as last_updated for a new entry; catalog ORDERING KEY (list/llms.txt/sitemap/OG sort by it)
sources:                    # non-empty array of public https URLs; MUST equal ## References (order + content)
  - https://...
related_services: []        # array of slugs, [] if none
lang: ko                    # exactly "ko" or "en" (per file; "both" produces two files)
logo: https://getdesign.kr/logos/samsung-one-ui.png   # optional; if set, ABSOLUTE getdesign.kr URL (not site-relative)
```

`CATEGORIES` (live source of truth, do not hardcode from memory): `finance, messenger, commerce, delivery, mobility, content, community, travel, gov, developer, education, career, etc`.

Key gotchas that block CI:
- `last_updated` / `created_at` must be `YYYY-MM-DD` strings; any other format throws.
- Omitting `created_at` is a **block** (`missing-created-at`), not a nit — the entry would sink to the bottom of the list.
- `logo` in frontmatter is the **absolute** `https://getdesign.kr/logos/...` form (portable when the md is copied out of the site). Preview HTML uses the **site-relative** `/logos/...` form instead.
- `sources` and `## References` are a **deliberate duplicate** — same order, same content. Never remove or one-side-edit them.

## 4. Naming conventions

| Field | Rule |
|---|---|
| `slug` | lowercase + hyphen + ASCII only; brand's Latin form preferred (`toss`, `line-design-system`, `vapor-ui`). Korean/space not allowed. |
| `name` | Korean company/brand display name (`구름`, `당근`, `라인`, `쏘카`). |
| `design_system_name` | Optional — the design system's own public name when distinct (`Vapor UI`, `SEED Design`, `SOCAR Frame 2.0`, `LINE Design System …`). |
| Section headings | English, fixed order, regardless of `lang`. |
| Color tokens | OKLCH **only** in values; family-step naming as published (`blue-500`, `gray-050`). |
| Token prose references | `{group.name}` form: `{colors.primary}`, `{typography.body-m}`, `{rounded.pill}`, `{component.button-primary}`. |
| Logo files | symbol at `{slug}.{ext}`; optional wordmark at `{slug}-logotype.{ext}` (preview hero only, no frontmatter field). |

For Samsung One UI: `slug: samsung-one-ui`, `name: 삼성 One UI`, `design_system_name: One UI`.

## 5. How sources are referenced

- Every concrete claim carries an inline `[src:N]` integer index pointing into the `sources` array (1-based, in order).
- `## References` mirrors `sources` exactly: one numbered entry per URL, same order. Each must be an **externally-accessible public URL** — no ephemeral/private handoff bundles (`api.anthropic.com/v1/design/h/...`), no `.claude/cache/...` paths, no label-only placeholders. Enforced by `non-public-reference` in `src/lib/source-citations.ts` (`pnpm validate:sources`).
- Citation is judged by **content match, not mere existence** — the reviewer spot-checks that `[src:N]` genuinely backs the claim.
- Reference descriptions may state *static facts about the source* ("this URL is a JS shell, must render", "values live at [src:N] not here") and cross-references, but not "N-th re-verification" history.
- **Audit-note convention** (when re-checking values against public sources): a `> **<label>(YYYY-MM-DD).** …` blockquote at the **head of the relevant section** (usually `## Colors`). One per section, overwritten on re-audit; date must be looked up, not remembered; editing the doc bumps `last_updated` (block-gated by `pnpm check:last-updated`). Per-token caveats go on the token's own trailing comment (the only path that reaches the tokens.json `note` field) — and never two hex on one token line.

## 6. How preview assets are generated

- Preview HTML is **hand-authored** (by the `preview-html-author` subagent in the skill, or by hand) as two self-contained files per entry: a hero on top + a component showcase grid below.
- They reference the shared runtime by absolute path: `<link rel="stylesheet" href="/preview/_runtime/tokens.css">` and `<script src="/preview/_runtime/iframe.js" defer>`. All page CSS is one inline `<style>`; no external JS frameworks.
- Tokens (colors/type/spacing/radius) are declared as CSS custom properties and applied to real components — the preview is a **component demo, not a swatch catalog** (standalone swatch grids and type-scale enumerations are machine-blocked; those live in the token cards instead).
- The **token sidecar** `{slug}.tokens.json` is generated by `pnpm tokens:build {slug}`, which extracts `name: oklch(...)` / `name: 16 / 24 / 700` / `name: 16px` lines from the md's fenced ```yaml blocks and tables. Alias rows (`fill-brand: blue-500`, `{colors.x}`) are intentionally skipped.
- The **OG image** is generated by `pnpm build:og` (Satori → PNG at `public/og/{slug}.png`).
- Serving: `/preview/*` and `/logos/*` get `Cache-Control: no-cache` (via `previewCacheHeadersPlugin` in `vite.config.ts`) so edits show without hard-refresh.
- A machine gate `pnpm validate:previews` hard-checks structure (data-theme/lang, absolute runtime paths, no foreign scripts, brotli transfer size ≤ 40 KiB, hero logo src, catalog disclosure strip, swatch/type-scale anti-patterns) and warns on responsive heuristics.

## 7. Are light/dark previews required?

**Yes — both are required.** Every entry ships `light.html` and `dark.html`. Constraints:

- `<html lang="{ko|en}" data-theme="{light|dark}">` — `data-theme` must match the filename.
- `dark.html` must be a **considered dark adaptation**, not a literal inversion — surfaces shift to brand-appropriate dark, primary lightness adjusted for contrast, all tokens rebound, text ≥ WCAG AA. A copy-paste that only flips `background`/`color` scores 0 on the light↔dark rubric item.
- `dark.html` is the **route default** (`src/routes/services/$slug.tsx`).
- **Exception in practice:** a genuinely light-mode-only system (e.g. `socar`, which publishes no dark palette) still ships a `dark.html` file but documents the light-only stance. For Samsung One UI this is moot — One UI has a first-class dark mode, so a real dark adaptation is expected.
- Both files carry the verbatim catalog disclosure strip as the first child of `<body>` (`class="catalog-disclaimer"`, containing `제휴·후원 관계가 없습니다` and `더미 데이터`).

## 8. Build, lint & test commands (CI gates)

```bash
pnpm typecheck && pnpm lint && pnpm format:check   # TS + eslint + prettier
pnpm test                # vitest (.claude/ excluded)
pnpm validate:catalog    # services/*.md: frontmatter, section order, OKLCH, citation integrity
pnpm validate:previews   # public/preview/*/ structure + responsive warns
pnpm tokens:check        # {slug}.tokens.json matches the source md (drift gate)
pnpm audit:oklch         # OKLCH ↔ paired hex consistency + preview vs md
pnpm check:last-updated  # branch-changed services/*.md have current last_updated (BLOCK)
pnpm build               # build:og + vite build
```

Single-file checks: `pnpm validate:draft <file.md> [--slug X --expected-logo <url> --lang ko]`, `pnpm validate:previews --slug <slug> --verbose`, `pnpm tokens:build <slug>`.

Package manager is **pnpm** (npm is forbidden). Node ≥ 22.22.2.

## 9. Contribution requirements

From `CONTRIBUTING.md` + `CLAUDE.md`:

- New entries are **recommended to go through the `/design-md` skill** (13-stage pipeline: preflight → research → author⇄review loop → user checkpoint → write md → tokens → preview loop → OG → verify). Hand-authoring is allowed but must self-validate with the same gates.
- Frontmatter must carry all required fields; `[src:N]` must match `sources` indices; both previews must open standalone; OG image generated.
- Brand-asset license/trademark concern must be reviewed (logos are each rights-holder's policy; see NOTICE). This matters for Samsung (see §C).
- Changes to files must be prettier-clean; unrelated mass reformatting must be a separate `style:` PR.
- `.claude/skills/design-md/` changes require prior issue agreement (not relevant to a catalog-only PR).
- PR uses the template's "카탈로그 PR 체크" checklist; CI (typecheck/lint/build) must pass.
- Content is licensed CC BY 4.0; code MIT; brand assets per rights-holder. Contributing implies agreement.

## 10. DCO / sign-off requirements

- The project uses the **Developer Certificate of Origin** (no CLA).
- Every commit must carry a `Signed-off-by:` trailer: commit with `git commit -s`. Configure `git config user.name` / `user.email` first.

- **Contribution hygiene for this work:** plain Korean conventional-commit subjects matching the repo's history, DCO sign-off trailer only — no extra trailers or tool banners in commit messages.

## 11. Five best reference entries for a Samsung One UI contribution

Best structural analogues are **published design systems with light+dark parity and a large component surface** — not product-brand entries. Ranked by template fit for an OS-level system:

### Ranking (best → worst template fit)

1. **seed-design (당근 / SEED Design)** — richest role-token model; explicit light+dark parity from the foundation layer; 40+ modular components; exemplary audit-note + public-package-reconciliation culture. Weak on breakpoint tokens.
2. **krds (KRDS, gov)** — most governance-mature; **the only one with an explicit breakpoint table** in Responsive Behavior; accessibility-first (high-contrast parity); 11 named composition Patterns. Light-leaning; ~38 components.
3. **bezier (Bezier)** — cleanest component taxonomy (59 Storybook stories, alpha/legacy/stable tiers); dual-theme autodocs; semantic role mapping over an 11-hue accent palette. No published breakpoint tokens.
4. **line-design-system (라인 / LDSG)** — multi-language maturity (EN/JP/TC/TH); elegant opacity-based state model (Hover 70% / Pressed 50%); cross-product 3-layer color abstraction. Sparse per-component specs, no published spacing ladder.
5. **socar (쏘카 / SOCAR Frame 2.0)** — Korean-native copy + touch-target rigor + one-handed UX principles; but **light-mode-only** and 375px-mobile-only scope, with several partial-spec components. Useful for interaction/UX detail, not as an OS template skeleton.

(Contrast — **toss** is a product-brand entry, not a system: 41 Figma-page component matrix + a 5-screen click-through + live JSX kit. Best viewed as an implementation exemplar, not a structural template.)

### Cross-comparison

| Dimension | seed-design | krds | bezier | line-design-system | socar |
|---|---|---|---|---|---|
| **Document structure** | 10 standard + Gradient subsection + Patterns(Loading) + Responsive + Known Gaps | 10 standard + Patterns(11 flows) + Responsive + Known Gaps | 10 standard + Responsive + Known Gaps | 10 standard + Border Width + Responsive + Known Gaps | 10 standard + Responsive + Known Gaps |
| **Specificity** | Highest — 252 light+dark tokens + manner-temperature scale | Very high — 4-layer tokens, exact breakpoints | Highest naming — 59 stories, tiered alpha/legacy | Moderate-high — opacity-state model, 43 colors | Moderate — 56 colors, light-only |
| **Design philosophy (Brand & Style)** | Role-as-color thesis; orange+lime dual identity | Trust/accessibility; "informational, neutral" gov voice | "Clean bright SaaS"; rainbow accents; squircle | "Quiet" family affinity; polite-teller tone | "Most SOCAR, most efficient"; cold/reserved |
| **Layout guidance** | Gutter/margin per breakpoint, concentric radius; no px breakpoints | **Explicit breakpoint table** (4 tiers, exact px), container 1248px | Theme-primary adaptation; no breakpoint tokens | Component-local; no published ladder | 375px baseline; no published breakpoints |
| **Component guidance** | 40+ `###`, token-referenced, few tsx | ~38 `###` + 11 patterns, HTML-like examples | 59 `###`, heavy tsx, variant enums | 59 `###`, tsx throughout | 24 `###` + haptic, tsx for core 5 |
| **Numerical tokens** | Mega YAML palette + role table (65 rows) | OKLCH fence + tables (colors/type/spacing/rounded) | YAML fences + theme-aware semantic table | YAML fences, OKLCH + hex comment | YAML fences per section, hex-commented |
| **Source attribution** | 37 sources (llms.txt endpoints), dense `[src:N]`, ΔE audit note | 7 sources, audit blockquotes | 5 sources (GitHub/npm/Storybook index), count-verified | 27 sources, provenance-correction note | 45 sources, JS-shell caveat, manual-render note |
| **LLM implementation guidance** | Role-token Do's, vendor-neutrality Don't, `{group.name}` refs | Emoji-ban, gradient-limit, vendor-neutrality Don't | Semantic-token Do's, alpha/legacy guidance, vendor-neutrality Don't | Opacity-rule Do's, naming-bound Don't | Semantic-token discipline, dark-estimation ban |
| **Preview structure** | Hero + showcase grid, light/dark pair, applied roles | Sticky gov-strip hero + showcase | Side-by-side light+dark autodocs feel | Hero + language/theme toggles | Light-only, sticky brand hero |

**Recommended primary template:** **seed-design** for the token/role architecture and dark-parity discipline, **borrowing krds's Responsive Behavior breakpoint table** (the one thing seed lacks that an OS system needs), and **bezier's component-taxonomy rigor** for enumerating One UI's large component surface.

## C. What could make an OS-level design system out of scope

Concerns to raise in the PR/issue before investing:

1. **Category fit.** `CATEGORIES` has no OS/platform slot. `developer` (One UI Design is published on Samsung's developer portal) or `etc` are the only defensible choices; every other entry is a Korean *service/product* or a *service's* design system. An OS skin is a different animal — the maintainer may want to scope-check whether a device-OS design language belongs in a catalog framed around "한국 브랜드의 디자인 시스템."

2. **Trademark / brand-asset policy.** Samsung is a strongly-protected trademark. `public/logos/*` are governed by each rights-holder's policy (NOTICE), and CONTRIBUTING explicitly asks contributors to check brand-asset policy and discuss concerns in an issue first. Safer to ship without a bundled Samsung logo (leave `logo` unset, note the TODO) than to embed a mark of uncertain license.

3. **Source availability & citability.** Samsung's design guidance is largely JS-rendered marketing/portal pages and Figma, not an open token package or `llms.txt` (unlike seed-design/line). The catalog requires **content-matching public citations**; if the concrete OKLCH/spacing values can't be traced to an accessible public source, many claims would have to be marked inferred (`≈`) — which weakens the entry and may not clear the brand-fidelity rubric. Confirm sufficient public, openable sources exist before authoring.

4. **Scope/size vs the catalog's grain.** One UI's component surface and multi-form-factor (phone/foldable/tablet/watch) responsive story is larger than any current entry. It's representable, but the entry must stay a *design-language summary* (intent + tokens + signature components), not attempt to mirror the full OS spec — otherwise it drifts from "design.md describes intent and tokens, not full components."

5. **Non-Korean-origin nuance.** The catalog's stated remit is Korean brands' design systems. Samsung is Korean, so this is a fit — but One UI is a global OS design language, so the entry should be careful not to over-localize claims that are actually global.
